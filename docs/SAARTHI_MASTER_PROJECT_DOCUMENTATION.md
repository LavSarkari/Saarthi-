## 1. PROJECT OVERVIEW & EXECUTIVE SUMMARY

### 1.1 Project Purpose & Vision
**Saarthi (सारथी)** is an AI-powered behavioral execution operating system designed to bridge the gap between planning commitments and completing them. 

Unlike traditional to-do applications (e.g., Todoist, Motion, Notion, Google Tasks) that function primarily as static repositories for user input, Saarthi acts as a proactive behavioral engine. It continuously monitors commitment progress, calculates real-time execution risk, handles prerequisite dependencies deterministically, auto-reschedules conflicting tasks, and intervenes proactively via multi-channel notifications (Web dashboard, Telegram, voice) when deadlines are at risk.

### 1.2 Core Architectural Philosophy
Saarthi is built on three fundamental architectural principles:

1. **Deterministic Authority**: All scheduling, prerequisite dependency handling, conflict resolution, risk scoring, notification escalation, and adaptive metrics are strictly governed by deterministic, mathematically verifiable algorithms in TypeScript. Gemini AI is utilized exclusively for natural language decomposition, syllabus OCR, voice synthesis, and context generation—**never** as a scheduling authority.
2. **Behavioral Proactivity**: The system assumes that human execution is subject to procrastination, overestimation, and friction. Saarthi actively detects stuck tasks, offers 30-second atomic "Micro Missions", generates mathematical scope compromises during deadline crises, and scales down notification frequency during burnout.
3. **Loop Protection & Idempotency**: All external integrations (Google Calendar, Telegram, background polling timers) enforce strict idempotency invariants. For example, Google Calendar events generated by Saarthi carry an explicit metadata tag (`Saarthi Exec:`) to prevent infinite synchronization feedback loops.

## 2. PROBLEM STATEMENT & PROPOSED SOLUTION

### 2.1 The Productivity Failure Spectrum
Traditional tools fail knowledge workers due to six fundamental execution breakdowns:

| Execution Failure Mode | Underlying Root Cause | Traditional Tool Behavior | Saarthi Solution |
| :--- | :--- | :--- | :--- |
| **Execution Paralysis** | High friction of starting creates cognitive avoidance | Displays static task with red overdue badge | Detects zero progress; launches 30s–5min **Micro Missions** |
| **Goal Overwhelm** | Large un-chunked commitments cause executive dysfunction | Requires manual breakdown by user | Gemini AI autonomously decomposes goals into minute-estimated subtasks |
| **Estimation Blindness** | Planning fallacy causes 2–5x time underestimation | Static deadlines remain unchanged until missed | **Pure Deterministic Adaptive Engine** adapts future task durations from actual historical velocity |
| **Dependency Cascades** | Delaying Task A invalidates dependent Task B and C | Manual rescheduling required for every task | **Phase 1 & 3 Rescheduling Engine** propagates downstream shifts across the Dependency DAG |
| **Shame Spirals** | Accumulation of red badges leads to tool abandonment | Sends repetitive high-pressure alerts | **Recovery OS** generates mathematical compromise plans (`reduce_scope`, `delay`, `split`, `skip`) |
| **Notification Fatigue** | Uncalibrated alerts cause users to ignore or mute app | Continuous linear reminders | **Phase 6 Escalation Engine** with monotonic stage progression & engagement back-off |

### 3.2 Dual-Persistence Architecture
Saarthi implements a dual-persistence strategy designed for high reliability, zero offline latency, and cloud synchronization:

1. **Client & Auth Cloud Layer (Firebase)**:
   - Client components ([`src/App.tsx`](file:///c:/Users/LavSarkari/Desktop/sarthi/src/App.tsx), [`src/lib/firebase.ts`](file:///c:/Users/LavSarkari/Desktop/sarthi/src/lib/firebase.ts)) utilize Firebase Auth for Google OAuth user authentication.
   - User tasks, settings, and companion profiles sync to Cloud Firestore for cross-device availability.

2. **Server Execution & Storage Engine (`src/services/localDb.ts`)**:
   - The Express backend operates an in-memory, crash-safe local JSON database engine backed by `data/local_db.json`.
   - **Atomic Write Protocol**: To prevent data corruption during process termination, `saveDb()` serializes state into `data/local_db.json.tmp` and executes `fs.renameSync()` for atomic file swapping.
   - **Corruption Recovery**: If `data/local_db.json` contains malformed JSON on startup, `loadDb()` catches the exception, creates a timestamped backup copy (`data/local_db.json.corrupt.<timestamp>`), and initializes a clean schema (`{ userSettings: {}, telegramLinks: {}, tasks: {} }`).
   - **Purpose**: Provides zero-latency reads/writes for background workers, Telegram polling, and deterministic rescheduling ticks without consuming Cloud Firestore API read/write quotas.

## 4. CORE EXECUTION ENGINES (PHASES 1–7)

### 4.1 Phase 1 — Prerequisite Dependency Graph Engine (`src/lib/dependencyGraph.ts`)
The dependency engine models task prerequisites as a Directed Acyclic Graph (DAG), where directed edges $(U \rightarrow V)$ denote that Task $U$ must be completed before Task $V$ can begin.

- **Topological Sorting (Kahn's Algorithm)**: Computes a valid linear execution order. Computes in-degrees for all nodes; nodes with in-degree 0 are processed first.
- **Cycle Detection (3-Color DFS)**: Detects circular dependencies $(A \rightarrow B \rightarrow C \rightarrow A)$ during graph validation using white (unvisited), gray (visiting), and black (visited) states. If a gray node is encountered, an explicit `AppError("CIRCULAR_DEPENDENCY")` is thrown.
- **Downstream Priority Elevation**: If a downstream task $V$ is classified as a `HARD` commitment or critical priority, all upstream prerequisite tasks in $V$'s transitive closure automatically inherit elevated priority to ensure the prerequisite is executed on time.

### 4.2 Phase 2 — Deterministic Scheduler Service (`src/services/deterministicSchedulerService.ts`)
The Phase 2 scheduler acts as the sole authority for allocating working slots for task subtasks.

- **Working Hours Allocation**: Subtasks are allocated into working windows (defaulting to 09:00–22:00 local time).
- **Subtask Time-Boxing**: Given total effort $E$ (minutes), subtasks are sequentially assigned non-overlapping start/end timestamps `[scheduledStart, scheduledEnd]`.
- **Conflict Detection**: If a task with `commitmentType === "HARD"` cannot be scheduled before its absolute deadline within available working capacity, the scheduler returns an explicit `CONFLICT` status rather than silently violating the deadline or truncating duration.

### 4.3 Phase 3 — Automatic Rescheduling Engine (`src/services/reschedulingService.ts`)
The Phase 3 rescheduling engine automatically repairs schedules when real-world execution deviates from the plan.

- **Trigger Taxonomy**:
  1. `TASK_DELAYED`: User or system reports delay on task execution.
  2. `TASK_COMPLETED_EARLY`: Early completion frees up capacity, unblocking downstream tasks.
  3. `TASK_MISSED`: Past-due incomplete task triggers downstream schedule recalculation.
  4. `DEPENDENCY_CHANGED`: Modification to task prerequisites triggers partial graph re-ordering.
- **Per-User Sequential Mutex Locking**: Prevents race conditions during concurrent trigger events by queuing execution per `userId`.
- **Minimal Graph Drift**: Only affected downstream dependent tasks are recalculated; unaffected independent sub-graphs remain locked to maintain schedule stability.

### 4.4 Phase 4 — Google Calendar Integration (`src/services/calendarService.ts`)
Synchronizes Saarthi schedule blocks with the user's primary Google Calendar.

- **Free/Busy Interval Extraction**: `fetchFreeBusyIntervals()` queries the Google Calendar API for busy intervals, normalizing them into `BusyInterval[]`.
- **Loop Protection**: Any calendar event with a summary starting with `Saarthi Exec:` is automatically filtered out from busy intervals to prevent Saarthi from treating its own synced events as external constraints.
- **Timezone Awareness**: All ISO date formatting enforces local timezone offsets via `formatLocalDateToIso()`.

### 4.5 Phase 5 — Commitment Semantics & Bills/Subscriptions (`src/services/taskService.ts`)
Differentiates commitments based on non-negotiability and financial consequences.

- **Commitment Types**:
  - `HARD`: Non-negotiable deadlines (e.g., exams, interviews, bill due dates). Must have an explicit deadline.
  - `FLEXIBLE`: Adjust-on-demand commitments (e.g., personal reading, optional practice).
- **Categories**: `EXAM`, `INTERVIEW`, `BILL`, `SUBSCRIPTION`, `MILESTONE`, `PERSONAL_FLEXIBLE`, `STUDY`.
- **Bill Lifecycles**:
  - `paymentStatus`: `UNPAID` $\rightarrow$ `PAID` or `OVERDUE`.
  - Overdue bills automatically receive $+35$ risk score escalation.
  - Transitioning payment status to `PAID` immediately suppresses further notification alerts.
- **Subscription Renewals**:
  - Automatically generates upcoming renewal instances with zero duplicate records across repeated evaluations.

### 4.6 Phase 6 — Notification Escalation & Override (`src/services/notificationService.ts`)
Manages proactive alerts across Web UI and Telegram.

- **Monotonic Stage Progression**: Stages transition strictly in sequence:
  $$\text{UPCOMING} \longrightarrow \text{APPROACHING} \longrightarrow \text{URGENT} \longrightarrow \text{CRITICAL} \longrightarrow \text{OVERDUE}$$
- **Keyed Deduplication**: Every dispatched notification key (`${taskId}:${stage}:${deadline}`) is stored in `deliveredNotificationKeys`. Duplicate evaluation checks skip already delivered stages to prevent alert spam across server restarts.
- **Critical Hard Override**: High-risk `HARD` commitments displace standard briefings and trigger immediate priority alerts.

### 4.7 Phase 7 — Pure Deterministic Adaptive Planning (`src/services/adaptivePlanningService.ts`)
Audits and eliminates all non-deterministic or random metrics from adaptive planning.

- **Zero Randomness Invariant**: Contains zero calls to `Math.random()`.
- **Mathematical Formulations**:
  - $\text{Completion Rate} = \frac{\text{Completed Tasks}}{\text{Total Tasks}}$
  - $\text{On-Time Rate} = \frac{\text{Completed On-Time Tasks}}{\text{Total Completed Tasks}}$
  - $\text{Miss Rate} = \frac{\text{Uncompleted Past-Due Tasks}}{\text{Total Tasks}}$
  - $\text{Average Delay} = \frac{\sum \text{Late Completion Delay Minutes}}{\text{Count of Late Completed Tasks}}$
- **Insufficient Data Threshold**: If observable task count $N < 3$, the engine returns `dataStatus: "INSUFFICIENT_DATA"` rather than generating artificial confidence scores.

## 5. OTHER SERVICES & INTELLIGENCE ENGINES

### 5.1 Risk Engine (`src/lib/riskEngine.ts`)
Computes real-time risk scores ($0–100$) and assigns visual risk zones:
- `safe`: Risk Score $0 – 39$ (Green)
- `watch`: Risk Score $40 – 69$ (Yellow)
- `critical`: Risk Score $70 – 100$ (Red)

**Risk Weight Factors**:
1. Velocity Ratio: Ratio of completed effort vs elapsed time.
2. Deadline Proximity: Time remaining relative to total estimated effort.
3. Commitment Type: $+15$ risk penalty for `HARD` commitments within $<24\text{h}$ of deadline.
4. Overdue Bills: $+35$ risk penalty for `UNPAID` bills past due date.

### 5.2 Activation Engine & Micro-Missions (`src/services/activationService.ts`)
Detects execution paralysis when a task has zero progress despite approaching deadlines.
- **Micro-Mission Generation**: Generates 30-second to 5-minute atomic starter actions (e.g., "Open document and write title").
- **Shrink-It Capability**: Allows users to reduce micro-mission effort by level up to 3 times if friction persists.

### 5.3 Recovery OS & Decision Matrix (`src/services/recoveryService.ts`)
Activates when completion becomes mathematically impossible. Generates compromise plans based on 4 recovery modes:
- `minimal`: Minor scope adjustments and small delays.
- `balanced`: Balanced trade-offs between scope reduction and deadline extensions.
- `maximum`: Aggressive scope compression to secure core pass/milestone criteria.
- `wellness`: Maximizes stress reduction by postponing non-critical commitments.

### 5.4 Behavioral Intelligence & Memory (`src/services/behavioralIntelligenceService.ts`)
Tracks user interaction across 23 behavioral event types (`TASK_CREATED`, `TASK_COMPLETED`, `FOCUS_SESSION_COMPLETED`, etc.) to build a private `LearningProfile` containing confidence-weighted learned attributes (preferred work hours, average focus duration, estimation error percentage).

### 5.5 Engagement & Back-Off Engine (`src/services/engagementService.ts`)
Monitors real-time user engagement score ($0–100$). Automatically activates back-off lockouts ($2\text{h} \rightarrow 6\text{h} \rightarrow 12\text{h}$) after consecutive ignored notifications and enforces user-configured quiet hours.
